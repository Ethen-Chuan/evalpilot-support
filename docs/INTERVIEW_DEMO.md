# 客服评测平台：3分钟面试演示

## 开场：这个项目解决什么问题

“客服能给出一段流畅的回答，不代表它真的回答对了。我做这个平台，是为了把客服质量变成可以检查、可以定位、可以再次测试的要求，而不是凭感觉判断好不好。”

## 1. 从具体客户问题开始

打开「客服模拟台」，选择「黑屏了，但我已经重启过」，保持「离线演示 / 规范答复示例」，点击「用这句话开始」。

可以这样讲：

“客户已经重启过，客服就不应该机械地让他再重启。我把保留上下文、不重复无效步骤、答复有知识依据等要求做成检查规则。”

## 2. 看评测能不能发现问题

点击右侧「对比两种示例答复」。两边使用相同的客户问题，左边是预先编写的问题答复，右边是按审核内容生成的规范答复。展开未通过的检查，指出对应问题。

“这里不是给两个模型排名，而是验证我的评测规则是否能抓到重复排查、错误承诺这些明确问题。答复是预设示例，规则检查和处理记录由系统实际执行。”

## 3. 解释六维评分

打开一段会话，再点击「评分标准」。

| 维度 | 权重 | 谁评 |
| --- | ---: | --- |
| 知识依据与适用性 | 25 | 系统检查 |
| 任务与动作合规 | 20 | 系统检查 |
| 上下文与对象连续性 | 15 | 系统检查 |
| 安全与业务诚实 | 20 | 系统检查 |
| 下一步的可执行性 | 15 | 人工判断 |
| 表达与用户体验 | 5 | 人工判断 |

“每维分0到4档，维度得分等于权重乘档位再除以4。系统能核验的部分占80分，答复是否好用、是否清楚，还需要人工评20分。人工没有评就保持待评，不补成100分。严重安全问题不能被高分抵消。”

如要现场提交人工评分，必须引用当前答复确实出现的原句，并写清楚评分理由；不要只为演示通过而给高分。

## 4. 保存案例，再检查一次

在对照页点击「查看问题答复并保存」，再点「保存为复测案例」。打开「复测案例」，找到刚才保存的案例，点击「再次测试」。

“我保留相同的客户输入，用规范答复示例重新运行检查。这里显示‘规则检查通过’，只代表预先规定的检查要求通过，不代表客户问题已经解决。”

旧版本记录会标为“仅供查看”，不要拿它做当前版本复测。请选择刚才现场新建的案例。

## 面试中可以承诺的边界

- 能现场演示：匿名案例对话、知识查阅记录、规则检查、六维评分、人工复核、同例对照、保存与复测。
- 离线演示不调用真实模型、不产生模型费用。不能把这些分数说成千问或DeepSeek的实测成绩。
- 真实模型连接需要在「模型设置」输入自己的普通API Key并单独授权测试；未验证的连接不进入运行列表。
- 不连接真实订单、退款、派单或人工坐席。交接内容只是本机草稿。
- 保存问题案例不等于训练模型，也不能说系统已经“自主学习”。本版演示界面已移除经验发布、候选审批和回滚入口。
- 权重和合格阈值是项目初版产品规则，尚未完成真实业务的双人评分校准，不称为行业标准。

## 可选加演：从业务决定解释本体，不先讲散点图

新版图谱入口：主导航「本体图谱」→「本体与语义演示」→「本体定义与图谱」。图谱页侧栏自动收起；如果窗口较窄，右上角「元素与证据」可以打开或收起对象面板，「全屏展示」提供更大画布。

先演示「叫法如何归一」：主机、机子、机器共同连到整机。点击对象展开下一层，下方「关系依据」读出关系方向；右侧查看定义与来源。「同码为何不同」保留完整 E102 · A-100 / E102 · A-200，避免把两个型号的候选部件混为一谈。所有关系仍是教学示例，不是已确认的维修结论。

要操作图谱，切到右侧「业务指令」，不是在「节点详情」中直接改数据。先预览，再确认；确认后才能说已经保存。目录和导航缩略图都按需展开，不必把整个画面挤成三列。

打开主导航「本体图谱」→「本体与语义演示」→「客服决策演示」。先讲任务：客户说“我的主机报 E102，开不了机”，现在是否有足够依据查故障知识、该如何继续？

1. 点击「运行这条客服任务」：缺少型号，故障知识查询没有执行、没有候选部件。它不是一条建议，而是实际被查询条件阻止。
2. 点击「补充 A-100 并继续」：重新检查条件，读取 A-100/E102 的知识。查看证据条目、候选和未核实事项；候选不是确诊，草稿不是工单。
3. 选「同码不同型号」再运行：A-200/E102 只引用另一条知识，不能套用主控板候选。展开被排除条目说明。
4. 选「口语也能找到规范知识」：对比字面候选与词典归一后的知识。点击第一步，看到“主机 → 整机”“开不了机 → 启动异常”；这是术语归一，不是在识别同一台真实设备。
5. 在执行记录中点「在图谱中核对这一步」，只看这一步实际用到的关系；可全屏，返回任务保留结果。不要把完整 Schema 中所有关系说成当前客户已经确认的事实。
6. 最后运行「12 条固定验收」，展开一条看预期与实际是否一致；可以展示「候选不能授权换件」中的拦截。

可以这样讲：“本体不负责自己编答案。它统一输入概念、限定知识适用范围；查询与动作约束把这些定义变成流程行为。图谱是这些决定的证据视图，评测则检查行为有没有符合预期。”

必须说明：“这是四条虚构知识上的确定性流程演示，不调用大模型。字面对照是简化检索，不代表真实 RAG 的水平；12 条是自编验收，不能证明生产准确率已经提高。真实收益还需要同一模型、同一标注集下的开关对照。”

「本体定义与图谱」保留全量、局部和逐级展开，供解释关系类型；不要让图谱操作抢在业务结果前面。六步记录只保留在当前页面，离开或刷新不保存；不能称为持久审计日志。

### 加演：现场改一个映射，证明图谱不是只读装饰

打开「本体定义与图谱」右侧「业务指令」，依次发送：

1. `运行客服任务“我的主机启动没反应。”`：先看到没有适用知识。
2. `给“启动异常”添加别名“启动没反应”`：解释改动预览，点击「确认执行本次修改」。
3. 再次发送第一句：知识查询使用了新映射，能看到实际引用编号；图上也新增叫法及关系。
4. `撤销上次修改`，确认后再发送第一句，行为回到修改前。

“这里实际调用了登记的本机业务函数，修改会持久保存，不是聊天回复假装操作成功。写入前有类型检查、固定验收和人工确认；图谱、词典与检索使用同一份定义。它只改教学工作区，不碰真实客服数据，也不是任意系统命令行。”

如果该别名已在之前演示中添加，不要声称第一次仍未命中。先查询记录核对当前状态，或换一个尚未登记的匿名新叫法。普通决策页的临时运行与指令窗口的持久操作记录是两种不同保存范围。

「真实语料关系」是另一个视图，显示现有人工标签与案例的真实关联，可以从节点回到完整会话核对。不在面试投屏时打开未经分享授权的客户对话或内部标签；本体概念演示优先使用虚构视图。详细边界见 [本体图谱说明](ONTOLOGY.md)。

## 一句话收尾

“这个项目的价值不是让客服看起来更聪明，而是让哪些地方答得不好有证据、让同样的问题下次还能再测。”
