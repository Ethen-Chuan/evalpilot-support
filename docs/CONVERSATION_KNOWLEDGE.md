# 完整对话资料与知识沉淀

## 为什么分成三层

**对话资料 → 知识草稿 → 答复知识。**

原始对话可能包含错答、反复追问和未解决的问题，应完整保存用于复盘，不应直接变成客服承诺。草稿保留原文依据，由业务人员纠正后明确确认发布；只有发布后的答复知识参与本地知识匹配。

## 完整对话阅读

「对话知识库」默认打开「对话资料」，左侧按会话而非单条回答列出记录。

- 本机会话按成功保存的问答顺序展开全部客户与客服发言；每轮关联真实 Trace、当时知识版本和用户反馈。
- 聊天试用台改为按会话读取完整历史，不再受首页“最近 30 条记录”的限制。测试覆盖 36 轮、72 条完整消息。
- 导入对话支持客户、智能客服、人工客服、系统和工具五种角色。正文逐字保留，多行内容不合并截断。
- 本轮搜索只高亮命中，不隐藏未命中的上下文；左侧搜索会检查整段消息内容。
- 默认以全文连续阅读方式展开全部消息，不在中间截断。可手动切换为紧凑滚动窗口；搜索支持逐处定位。
- 原记录未提供时间时明确标示缺失，不捏造时间或 Trace。上报角色和时间不代表平台验证过其真实性。
- 被隐私门禁拒绝的本机输入不保存原文；失败执行见 Trace。本机会话完整性说明不会把被阻断的数据伪装成已保存。

## 整段分析

分析读取全量会话，提供可定位到原文的规则信号：归一化后的重复问题、本地负反馈、建议转人工、已观测答复缺少知识依据、导入的人工回复、末条客户发言未见后续答复。

本地分类意图可组成话题路径，知识引用按版本聚合。导入原文没有意图标签时，不编造自动主题或引用。统计轮数以客户发言条数计；连续用户消息不强行拼成假问答。

这是规则与已有元数据分析，**不是大语言模型理解全文后的自动复盘**，也不会根据客服回复了就认定已解决。业务正确性、最终解决情况与根因仍需人工核实。

## 整段存档与版本

「整段存入知识库」保存不可被此接口覆盖的完整快照：所有消息、来源、角色、顺序、已提供的时间、每轮 Trace 引用、分析结果和 SHA-256 指纹。

- 相同消息与元数据重复保存，返回既有版本，不生成重复资料。
- 新消息或反馈变化后，保存为新的资料版本；旧版本不覆盖。
- 保存请求携带阅读时的消息指纹，内容已变化会要求刷新，防止把旧视图保存成“当前完整对话”。
- 版本选择器可对照“最新完整会话”和各个冻结版本；正文导出覆盖所选版本全部消息。
- 指纹用于完整性核对，不等于业务真实性保证、审计签名或不可篡改存储。

## 整理与审核

1. 在完整会话勾选依据，可跨多轮选择；至少包含一条客户消息与一条客服 / 人工答复。
2. 整理知识草稿前，系统确保整段原文已存档。选中的文字原样展示在对照区。
3. 手工编辑知识标题、适用问题与前提、标准答复和匹配词。原回答可能错，默认复制只是编辑起点，不是自动正确提炼。
4. 保存草稿不改变原对话，也不加入答复知识。
5. 在草稿页复核原文，明确勾选已核对上下文与业务政策，填写匹配词后才能发布。草稿版本过期会拒绝覆盖。
6. 发布记录包含来源会话、冻结版本、消息编号、源指纹和本机确认时间。答复知识有“查看完整来源对话”入口。

当前只有本机操作确认，没有账号、审核人身份认证、双人审批或权限隔离；不能冒充企业审核流程。审核测试在独立测试数据库进行，不修改演示工作区的有效政策。

## 导入格式

用户需先完成授权和人工脱敏确认，服务器扫描所有消息与标题 / 来源说明，全部通过后一次性保存。遇到超限、错误角色、隐私风险、缺失扫描器或无法转换的内容，整次拒绝，不部分导入。

### 带角色标签的文本

```text
客户：第一条问题
客服：第一条答复的第一行
答复的第二行
客户：后续追问
人工客服：人工回复
```

可用标签：客户 / 用户、客服 / 助手 / 智能客服、人工 / 人工客服、系统、工具。新角色标签需在行首，其余行继续上一条消息。如果消息正文中也包含行首角色标签，使用 JSON 以免分段歧义。

### JSON

```json
[
  {"role":"user","content":"第一条匿名问题","at":"2026-10-10T09:00:00+08:00"},
  {"role":"assistant","content":"客服回复\n第二行","at":"2026-10-10T09:00:03+08:00"},
  {"role":"user","content":"追问"},
  {"role":"human","content":"人工回复"}
]
```

也接受带 `messages` 数组的对象。角色枚举：`user`、`assistant`、`human`、`system`、`tool`。每条消息仅支持 `role`、`content`、可选 `at`。时间需有时区且不能倒退；未知字段会拒绝，避免悄悄丢失附件、工具调用参数或其他上下文。需要导入其他系统格式时，先转换为此协议。

限制：一次 2–200 条消息，单条不超过 12,000 字符，全体文本不超过 100,000 字符；本地文件须为 UTF-8 `.txt` / `.json` 且不超过 200 KB，HTTP 请求不超过 256,000 字节。界面在序列化超限时提醒分卷，**不会静默截断**。文件名、附件、截图和二进制内容不上传。

上传者可在浏览器编辑匿名副本；本地原文件不会覆盖。平台不能验证上游是否已经删减，因此“完整”指完整保留本次提供的消息，而不是保证已拿到上游所有数据。

## API 与存储

- `GET /api/support/sessions`：会话列表、全量原文搜索；支持 `q/status/page`。
- `GET /api/support/sessions/{id}`：完整会话、规则分析和归档版本。
- `GET /api/support/sessions/{id}/turns`：本机完整问答历史，不受最近记录数量限制。
- `POST /api/support/sessions/import`：导入完整匿名会话。
- `POST /api/support/sessions/{id}/archive`：携带当前 `hash` 冻结整段资料。
- `GET /api/support/dialogue-archives/{id}`：冻结版本详情；追加 `/export.md` 导出全部原文。
- `GET /api/support/sessions/{id}/export.md` 或 `/export.json`：导出最新完整记录。
- `GET/POST /api/support/knowledge-drafts`：查看或创建草稿。
- `POST /api/support/knowledge-drafts/{id}`：版本检查后保存，或提交显式审核确认。

资料、导入原文、草稿和有效知识存放在本地 SQLite，服务重启后保留。仅本机演示使用，没有生产级鉴权、数据保留 / 删除策略或大规模查询优化。

## 对外分享门禁

自动规则未发现明确敏感项不代表绝对安全。分享正文或导出物前，仍需检查人名、地址、公司 / 客户 / 项目名称、订单信息、异常内容及其他上下文。不要公开完整数据库。图片、附件和复杂文件不在本次文本导入能力范围内。
